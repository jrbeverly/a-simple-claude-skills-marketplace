# Documentation Standards Skill

Document a new or existing repository to the project's documentation standards using the bundled templates. Each template is designed to be copied into a fresh project and used with no edits beyond filling in placeholders.

## When to use this skill

- A new repository needs its initial documentation scaffold.
- An existing repository is missing one or more standard documents (README, CODEMAP, ADRs, CHANGELOG).
- A contributor asks "how should I document this?" or "what goes in CODEMAP.md?"

## Templates and when to apply them

### README (`templates/readme.md`)

The first document a visitor reads. Apply when:
- A repository has no README.
- The existing README is autogenerated or empty.
- The project has grown beyond the original README's scope.

The template covers: project name and one-line purpose, what the project provides, quickstart with prerequisites, usage examples, configuration reference, and pointers to further reading.

### CODEMAP (`templates/codemap.md`)

The repository map for contributors and AI assistants. Apply when:
- A repository has no CODEMAP.
- The repository structure, technology stack, or architecture has changed.
- An AI assistant needs to understand the repository layout.

The template covers: purpose statement, top-level layout table, technology stack with deviations from defaults, build and test commands, specification documents, architecture decisions, architecture patterns, and key invariants.

### ADR (`templates/adr.md`)

Architecture Decision Record for capturing design decisions with rationale. Apply when:
- Making a significant technology choice (language, framework, database, protocol).
- Deviating from established preferences or defaults.
- Choosing between competing approaches where the trade-offs matter.

The template covers: status, context (why this decision is needed), decision (what was chosen), rationale (why this option over alternatives), trade-offs (what is given up and how it is mitigated), and consequences (what changes because of this decision).

Follow the ADR numbering convention: `NNNN-title-in-kebab-case.md` under `docs/decisions/`. Use the next available four-digit number.

### CHANGELOG entry (`templates/changelog-entry.md`)

Human-readable summary of changes per release. Apply when:
- A repository has no CHANGELOG.
- A new release is being cut and the CHANGELOG needs an entry.

The template follows [Keep a Changelog](https://keepachangelog.com/) conventions with sections for Added, Changed, Deprecated, Removed, Fixed, and Security. Each entry links to the version's comparison URL and lists changes in bullet form.

## How to use the templates

1. Identify which documents are missing from the target repository.
2. Copy the relevant template from this skill's `templates/` directory into the target repository.
3. Fill in every placeholder (marked with `<!-- -->` comments or `{{placeholder}}` syntax).
4. Remove the explanatory comments once filled in.
5. Commit each document separately with a `docs:` Conventional Commits message.

## Documenting a repository from scratch

For a brand-new repository, apply the templates in this order:

1. **README.md** — top-level, explains what the project is and how to get started.
2. **CODEMAP.md** — maps the repository for contributors and AI assistants.
3. **docs/decisions/0001-initial-architecture.md** — captures the initial technology and architecture decisions.
4. **CHANGELOG.md** — starts with an `[Unreleased]` section, populated on first release.

## Conventions

- All documentation files are Markdown (`.md`).
- Headings use ATX style (`#`), not setext (`===`).
- Code blocks are fenced with triple backticks and include a language identifier.
- Links use reference style when the same URL appears multiple times; inline style otherwise.
- Placeholders are clearly marked so a reader knows what to replace.
- Every template is self-contained: copy, fill placeholders, done.
